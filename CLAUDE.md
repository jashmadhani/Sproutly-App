# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

The **App Store build** of Sproutly — an offline child-development milestone tracker. iOS 17+, iPhone-only, portrait-only, Swift 6 strict concurrency, SwiftUI + SwiftData, zero network calls. This is the shipping lineage; the public `.swiftpm` repo at `~/Projects/Sproutly` is the older Playgrounds archive with a single-child model and no Pro features, and changes do not flow between them automatically.

One app, shipped free, with **Sproutly Pro** as a $9.99 one-time non-consumable unlock inside it. There is no separate paid build.

## Project generation and building

The `.xcodeproj` is **generated by XcodeGen and not committed**. `project.yml` is the single source of truth.

```sh
xcodegen generate && open Sproutly.xcodeproj
```

Re-run `xcodegen generate` after any `project.yml` change or when files are added. **Never** configure capabilities, build settings, Info.plist keys, or scheme options through the Xcode GUI — those edits live in the generated project and are destroyed on the next generate. Info.plist is generated from `INFOPLIST_KEY_*` entries in `project.yml`; there is deliberately no checked-in Info.plist.

Building/testing is done in Xcode (⌘R / ⌘U); a single test runs from the diamond gutter icon. Verify changes by asking the user to run in Xcode.

## StoreKit and Pro gating

- `Managers/PurchaseManager.swift` — `@MainActor @Observable`, injected app-wide. One product, `com.jashmadhani.Sproutly.pro`, family-shareable.
- `isPro` is written **only** from verified entitlements (`Transaction.currentEntitlements`, rejecting `revocationDate != nil`). There is no debug override and no cached bool; entitlements are re-checked every launch so refunds and Family Sharing revocations take effect. Don't add a shortcut flag.
- `hasCheckedEntitlements` exists because `isPro == false` before the first check means *unknown*, not *unpurchased* — gating on it directly flashes a paywall at a paying customer.
- A `Transaction.updates` listener starts in `init()`, not from a view, so Ask-to-Buy approvals and cross-device purchases land even with no paywall on screen. Every transaction must be `finish()`ed.
- The scheme wires `Sproutly.storekit` as `storeKitConfiguration` (see `project.yml` `schemes:`), so simulator purchases work with no sandbox account and no real money. `PurchaseManagerTests` asserts the product ID matches that file — keep them in sync.
- The paywall is reach-triggered only, via a `PaywallReason` per entry point; never shown at launch. Gates today: second child (`SettingsView`), milestone photos, custom milestones, share cards (`MilestonesView`), PDF report (`DashboardView`). Everything else is free.

## Architecture

**Children own milestones.** `Child` and `Milestone` are both `@Model`; `Child.milestones` is a `.cascade` relationship with `inverse: \Milestone.child`. Every child gets their **own copy** of the full seeded milestone set (`DataSeeder.seed(for:in:)`), so siblings never share progress. Views must go through `ChildStore.activeChild` rather than querying `Milestone` globally — a global `@Query` bleeds one child's progress into another's screen.

**`ChildStore`** (`@MainActor @Observable`, constructed with the container's `mainContext`) owns the roster, the active selection (persisted as a UUID string in `UserDefaults` key `sproutly_active_child_id`), and `needsOnboarding` / `hasMultipleChildren`. Mutations call `save()` then `refresh()`; `refresh()` re-resolves `activeChild` and falls back to the first child so the app is never pointing at nothing.

**Container construction is defensive on purpose** (`MyApp.swift`). A named `ModelConfiguration` resolves to `Library/Application Support/SproutlyDB.store`, a directory SwiftData will *not* create — the app black-screened on first launch without the explicit `createDirectory`. There is then a three-tier fallback: normal open → archive the unreadable store aside (timestamped, `.store`/`-shm`/`-wal`) and retry → in-memory for the session. Don't simplify this into a `try!`.

**Legacy import.** `ChildStore.importLegacyProfileIfNeeded()` runs once from `ContentView.task` and adopts pre-multi-child data — the old `UserDefaults` profile (`sproutly_profile`, legacy `elitegrowth_profile`) plus any `Milestone` with `child == nil` — into a real `Child`. It's idempotent and clears the legacy keys.

**Schema.** `SproutlySchemaV1` (aliased `SproutlyCurrentSchema`) is the first schema to reach the App Store, so `SproutlyMigrationPlan.stages` is empty. To change a model: freeze a copy of the *current* models in a new `SproutlySchemaV2` enum and add a stage — never re-point an existing `VersionedSchema` at edited model classes, which silently breaks migration.

**Corrected age is the central concept.** `Child.calculateCorrectedAge()` subtracts `(40 - gestationalWeeks) / 4.33` months for premature children. Milestone logic keys off corrected age; `humanReadableAge` (chronological, for greetings) and `ageText` (corrected) differ deliberately.

**Domain scoring.** `Managers/DevelopmentObserver.swift` is the pure, testable core: milestones + corrected age → per-domain ratios and a `DomainStatus` (`onTrack` ≥0.75, `emerging` ≥0.50, `needsSupport` ≥0.30, else `worthDiscussing`). Only milestones at or below corrected age count, and Language carries a sensitivity weight. `DashboardViewModel.update(milestones:child:)` recomputes manually behind a hash signature — it is not reactive, so any path that mutates milestones must let `update` run again.

**User-created milestones are inert.** `Milestone.isUserCreated` marks parent-authored moments, which are excluded from domain scoring (`DevelopmentObserver`), from report expectations (`ReportBuilder` lists them separately as "own moments"), from `isSignificantlyLate`, and from `DataSeeder.reseedIfIncomplete`'s repair path. Any new logic that classifies or judges progress must filter them out too.

**Photos are files, not blobs.** `Managers/PhotoStore.swift` writes downscaled JPEGs (1600px long edge, 0.8 quality) into `Application Support/MilestonePhotos`; `Milestone.photoFilename` stores only the name. Never put image data in SwiftData. Deleting a milestone must also `PhotoStore.delete` its file.

**Sharing.** `ReportBuilder.build(for:)` produces a `MilestoneReport` value; `ShareRenderer` turns it into a PDF (pediatrician report) or a milestone share card PNG, both written to temp URLs handed to `ShareSheet`. Rendering is separate from building so the report is testable without a graphics context.

**Assistant is rule-based, not an LLM.** `Views/SupportAssistantView.swift` holds a keyword→category→weight table plus one hand-written response per `MilestoneCategory`. Never introduce a network call here.

**Theming.** `Theme.swift` exposes only `static func x(for nightMode: Bool) -> Color` — no adaptive asset colors. `ThemeManager` (`@Observable`, `UserDefaults` key `nightModeEnabled`) resolves them and drives `.preferredColorScheme`. Views use `@Environment(ThemeManager.self)` with `theme.card`, `.warmCard(nightMode:)`, `AmbientBackground`. Don't hardcode a `Color` in a view.

**Category strings.** `Milestone.category` is a `String` bridged via `categoryType`. Values must exactly match `MilestoneCategory` raw values (`"Gross Motor"`, `"Fine Motor"`, `"Language"`, `"Cognitive"`, `"Social-Emotional"`) — a typo silently falls back to `.grossMotor`.

## Privacy and store constraints

- App Privacy must stay **Data Not Collected**. `Resources/PrivacyInfo.xcprivacy` declares no tracking, no collected data types, one accessed-API reason (`CA92.1`, `UserDefaults`). Anything that adds an API requiring a reason, or moves data off-device, invalidates both this and the privacy policy.
- `INFOPLIST_KEY_NSPhotoLibraryUsageDescription` lives in `project.yml` and is required — a missing usage string is a launch-time crash and a review rejection.
- Category is **Lifestyle**, not Health & Fitness: copy stays educational and never diagnoses. Onboarding carries a required medical disclaimer step.
- Tone is a hard product requirement — reassuring, non-alarming, never a scorecard. The paywall follows the same rule: no urgency language, no launch nag.
