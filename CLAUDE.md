# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

The **App Store build** of Sproutly — an offline child-development milestone tracker. iOS 17+, iPhone-only, portrait-only, Swift 6 strict concurrency, SwiftUI + SwiftData, zero network calls. This is the shipping lineage; the public `.swiftpm` repo at `~/Projects/Sproutly` is the older Playgrounds archive with a single-child model and no Pro features, and changes do not flow between them automatically.

One app, shipped free, with **Sproutly Pro** as a $9.99 one-time non-consumable unlock inside it. There is no separate paid build.

## Project generation and building

The `.xcodeproj` is **generated by XcodeGen and not committed**. `project.yml` is the single source of truth.

```sh
xcodegen generate && open Sproutly.xcodeproj
```

Re-run `xcodegen generate` after any `project.yml` change or when files are added. **Never** configure capabilities, build settings, Info.plist keys, or scheme options through the Xcode GUI — those edits live in the generated project and are destroyed on the next generate. Info.plist is generated from `INFOPLIST_KEY_*` entries in `project.yml`; there is deliberately no checked-in Info.plist.

Building/testing is done in Xcode (⌘R / ⌘U); a single test runs from the diamond gutter icon. Verify changes by asking the user to run in Xcode.

## StoreKit and Pro gating

- `Managers/PurchaseManager.swift` — `@MainActor @Observable`, injected app-wide. One product, `com.jashmadhani.Sproutly.pro`, family-shareable.
- `isPro` is written **only** from verified entitlements (`Transaction.currentEntitlements`, rejecting `revocationDate != nil`). There is no debug override and no cached bool; entitlements are re-checked every launch so refunds and Family Sharing revocations take effect. Don't add a shortcut flag.
- `hasCheckedEntitlements` exists because `isPro == false` before the first check means *unknown*, not *unpurchased* — gating on it directly flashes a paywall at a paying customer. Gates that **present the paywall** must therefore call `await purchases.isUnlocked()`, which awaits that first check, rather than reading `isPro`. Reading `isPro` directly is fine for display-only state (a "Pro" badge, a section that appears once unlocked), where being briefly wrong self-corrects.
- A `Transaction.updates` listener starts in `init()`, not from a view, so Ask-to-Buy approvals and cross-device purchases land even with no paywall on screen. Every transaction must be `finish()`ed.
- The scheme wires `Sproutly.storekit` as `storeKitConfiguration` (see `project.yml` `schemes:`), so simulator purchases work with no sandbox account and no real money. `PurchaseManagerTests` asserts the product ID matches that file — keep them in sync.
- The paywall is reach-triggered only, via a `PaywallReason` per entry point; never shown at launch. Gates today: second child (`SettingsView`), milestone photos, custom milestones, share cards (`MilestonesView`), PDF report (`DashboardView`). Everything else is free.

## Architecture

**Children own milestones.** `Child` and `Milestone` are both `@Model`; `Child.milestones` is a `.cascade` relationship with `inverse: \Milestone.child`. Every child gets their **own copy** of the full seeded milestone set (`DataSeeder.seed(for:in:)`), so siblings never share progress. Views must go through `ChildStore.activeChild` rather than querying `Milestone` globally — a global `@Query` bleeds one child's progress into another's screen.

**`ChildStore`** (`@MainActor @Observable`, constructed with the container's `mainContext`) owns the roster, the active selection (persisted as a UUID string in `UserDefaults` key `sproutly_active_child_id`), and `needsOnboarding` / `hasMultipleChildren`. Mutations call `save()` then `refresh()`; `refresh()` re-resolves `activeChild` and falls back to the first child so the app is never pointing at nothing.

**Container construction is defensive on purpose** (`MyApp.swift`). A named `ModelConfiguration` resolves to `Library/Application Support/SproutlyDB.store`, a directory SwiftData will *not* create — the app black-screened on first launch without the explicit `createDirectory`. There is then a three-tier fallback: normal open → archive the unreadable store aside (timestamped, `.store`/`-shm`/`-wal`) and retry → in-memory for the session. Don't simplify this into a `try!`.

**Legacy import.** `ChildStore.importLegacyProfileIfNeeded()` runs once from `ContentView.task` and adopts pre-multi-child data — the old `UserDefaults` profile (`sproutly_profile`, legacy `elitegrowth_profile`) plus any `Milestone` with `child == nil` — into a real `Child`. It's idempotent and clears the legacy keys.

**Schema.** `SproutlySchemaV1` (aliased `SproutlyCurrentSchema`) is the first schema to reach the App Store, so `SproutlyMigrationPlan.stages` is empty. To change a model: freeze a copy of the *current* models in a new `SproutlySchemaV2` enum and add a stage — never re-point an existing `VersionedSchema` at edited model classes, which silently breaks migration.

**Corrected age is the central concept.** `Child.calculateCorrectedAge()` subtracts `(40 - gestationalWeeks) / 4.33` months for premature children. Milestone logic keys off corrected age; `humanReadableAge` (chronological, for greetings) and `ageText` (corrected) differ deliberately.

**Domain scoring.** `Managers/DevelopmentObserver.swift` is the pure, testable core: milestones + corrected age → per-domain ratios and a `DomainStatus` (`onTrack` ≥0.75, `emerging` ≥0.50, `needsSupport` ≥0.30, else `worthDiscussing`). Only milestones at or below corrected age count, and Language carries a sensitivity weight. `DashboardViewModel.update(milestones:child:)` recomputes manually behind a hash signature — it is not reactive, so any path that mutates milestones must let `update` run again.

**User-created milestones are inert.** `Milestone.isUserCreated` marks parent-authored moments, which are excluded from domain scoring (`DevelopmentObserver`), from report expectations (`ReportBuilder` lists them separately as "own moments"), from `isSignificantlyLate`, and from `DataSeeder.reseedIfIncomplete`'s repair path. Any new logic that classifies or judges progress must filter them out too.

**Photos are files, not blobs.** `Managers/PhotoStore.swift` writes downscaled JPEGs (1600px long edge, 0.8 quality) into `Application Support/MilestonePhotos`; `Milestone.photoFilename` stores only the name. Never put image data in SwiftData. Deleting a milestone must also `PhotoStore.delete` its file.

**Sharing.** `ReportBuilder.build(for:)` produces a `MilestoneReport` value; `ShareRenderer` turns it into a PDF (pediatrician report) or a milestone share card PNG, both written to temp URLs handed to `ShareSheet`. Rendering is separate from building so the report is testable without a graphics context.

**Assistant is rule-based, not an LLM.** `Views/AssistantView.swift` is the tab screen (header + scroll chrome); `Views/SupportAssistantView.swift` holds the actual logic — a keyword→category→weight table plus one hand-written response per `MilestoneCategory`. Never introduce a network call here.

**Theming.** `Theme.swift` exposes only `static func x(for nightMode: Bool) -> Color` — no adaptive asset colors. `ThemeManager` (`@Observable`, `UserDefaults` key `nightModeEnabled`) resolves them and drives `.preferredColorScheme`. Views use `@Environment(ThemeManager.self)` with `theme.card`, `.warmCard(nightMode:)`, `AmbientBackground`. Don't hardcode a `Color` in a view.

**Category strings.** `Milestone.category` is a `String` bridged via `categoryType`. Values must exactly match `MilestoneCategory` raw values (`"Gross Motor"`, `"Fine Motor"`, `"Language"`, `"Cognitive"`, `"Social-Emotional"`) — a typo silently falls back to `.grossMotor`.

## Privacy and store constraints

- App Privacy must stay **Data Not Collected**. `Resources/PrivacyInfo.xcprivacy` declares no tracking, no collected data types, one accessed-API reason (`CA92.1`, `UserDefaults`). Anything that adds an API requiring a reason, or moves data off-device, invalidates both this and the privacy policy.
- `INFOPLIST_KEY_NSPhotoLibraryUsageDescription` lives in `project.yml` and is required — a missing usage string is a launch-time crash and a review rejection.
- Category is **Lifestyle**, not Health & Fitness: copy stays educational and never diagnoses. Onboarding carries a required medical disclaimer step.
- Tone is a hard product requirement — reassuring, non-alarming, never a scorecard. The paywall follows the same rule: no urgency language, no launch nag.

## UX writing and Sproutly voice

Tone and language are a hard product requirement.

Sproutly is a parent-oriented lifestyle and child-development companion. Its language should feel like it was written by someone who understands what parents actually notice, wonder about, and want to remember.

The UI should feel:
- calm
- human
- reassuring
- practical
- thoughtful
- parent-first
- clear
- conversational

It should NOT feel:
- AI-generated
- corporate
- like startup marketing copy
- overly sentimental
- overly cute
- academic
- clinical
- like a healthcare dashboard

### Core writing principle

Write for a parent, not for a product specification.

The ideal reaction to a sentence is:

"That's exactly what I was thinking."

Not:

"That's a polished sentence."

Prefer concrete, natural language over emotional or inspirational language.

For example:

BAD:
"Look back on your journey with warmth."

BETTER:
"See how much your child has changed over time."

BAD:
"Milestones will be gently adjusted."

BETTER:
"We'll take that into account when showing milestones."

BAD:
"That's it. Simple, gentle, yours."

BETTER:
"Notice it. Save it. Come back to it."

BAD:
"Child's Name"

BETTER:
"What do you call your little one?"

BAD:
"Recent Moments"

BETTER:
"What you've noticed"

These are examples of the writing direction, not mandatory replacements.

### Avoid AI-sounding language

Do not repeatedly use words or phrases such as:

- gentle
- journey
- beautiful
- meaningful moments
- little moments
- bloom
- celebrate
- with warmth
- beautifully unique
- quiet growth
- gentle discovery
- precious moments
- magical
- wonderful journey

These words are not forbidden individually. Avoid repetitive or artificial emotional language.

Do not add emotional language merely to make a sentence sound warm.

The existing visual design already communicates warmth. The copy should provide clarity and personality.

### Parent-first vocabulary

Prefer language based on what parents actually do:

- notice
- see
- save
- remember
- look back
- learn
- explore
- try
- play
- grow
- discover
- keep track

Use "noticed" or "saved" where appropriate instead of unnecessarily formal product terminology.

Milestones should feel like things a parent notices, not tests a child passes.

Avoid language that makes parents feel as though they are being graded.

### Child-development language

Child-development terminology may be used when necessary for accuracy, but user-facing copy should prefer ordinary parent-friendly explanations.

Do not unnecessarily make the application sound clinical or academic.

For example:

Prefer:

"Five ways children grow"

over:

"The Five Developmental Domains"

Prefer:

"Keeping an eye on how your child is growing"

over:

"Developmental Surveillance"

Prefer:

"What you've noticed"

over:

"Developmental Observations"

when the underlying functionality supports that wording.

Do not invent terminology merely to make the product sound sophisticated.

### Do not alter meaning to improve tone

Do not change factual meaning, calculations, milestone logic, corrected-age logic, or safety-related behavior merely to make copy sound friendlier.

If existing terminology is required because it describes an actual product behavior, retain the underlying meaning and find the clearest parent-facing explanation.

If you encounter language that appears unnecessarily clinical, flag it and propose a parent-friendly alternative.

### Onboarding

Onboarding should feel like a calm introduction from a product that understands parents.

Avoid startup-style positioning.

Avoid inspirational slogans.

The parent should quickly understand:

- what Sproutly does
- why it is useful
- how it works
- why information is being requested

Use natural language.

For example:

Instead of:

"Observe → Log → Reflect"

consider language based on the actual experience:

"Notice → Save → Look back"

Do not change the interaction model solely because of this wording preference.

### Dashboard

The dashboard should feel like a personal snapshot of the child's development.

It should not feel like an analytics dashboard.

Prefer:

"What you've noticed"

over:

"Recent Observations"

Prefer:

"Things worth knowing"

over:

"Growth Insights"

Prefer:

"Five ways children grow"

over:

"The Five Domains"

when the surrounding content supports it.

### Milestones

Milestones are observations, not grades.

Avoid language implying that a child has:
- passed
- failed
- achieved a score
- fallen behind
- completed an assessment

unless the underlying feature genuinely requires that terminology.

When a parent records a milestone, the interaction should feel like:

"I noticed my child doing this."

rather than:

"I checked another item off a checklist."

### Memory and notes

Memory-related interactions should feel personal but not sentimental.

Prefer:

"Save this moment"

"Add a note"

"What did you notice?"

"Anything you want to remember?"

over exaggerated emotional language.

### Educational content

Educational sections should sound like a knowledgeable parenting guide.

Use:
- short paragraphs
- concrete examples
- everyday language
- clear explanations

Avoid:
- textbook-style introductions
- unnecessary jargon
- academic phrasing
- generic research-summary language
- dramatic claims

### Settings

Settings should explain features in terms parents understand.

For example:

Instead of:
"Milestones will be gently adjusted."

Prefer:
"We'll take that into account when showing milestones."

Do not use "gentle" as a substitute for explaining what a feature actually does.

### Accessibility

Apply the same writing principles to:

- accessibilityLabel
- accessibilityHint
- accessibilityValue
- VoiceOver text

Accessibility copy must remain concise and functional.

Do not make accessibility descriptions artificially conversational.

### Product-specific terminology

Maintain consistency across the application.

Before changing terminology, search the entire repository and determine where the term is used.

Do not perform blind global replacements.

For important concepts, choose one primary term and use it consistently.

Examples that require deliberate decisions:

- child vs little one
- milestone vs skill
- noticed vs completed
- growth vs development
- moment vs memory
- note vs memory

Context may justify exceptions.

### Code comments

Developer comments are separate from user-facing copy.

Do not rewrite comments simply to make them sound more human.

Only change comments when they:
- are incorrect
- describe behavior that has changed
- are unnecessarily verbose
- contain misleading information
- document a non-obvious implementation decision incorrectly

Keep developer comments concise and technical.

### UX writing audit workflow

When asked to improve Sproutly's copy:

1. Scan the entire repository.
2. Find all user-facing strings.
3. Find accessibility strings.
4. Find relevant developer comments.
5. Group copy by feature.
6. Identify repetitive, generic, AI-sounding, overly clinical, or overly sentimental language.
7. Establish consistent terminology.
8. Propose major changes before making them.
9. Implement the changes.
10. Search again for the old terminology.
11. Build the project.
12. Check for clipping, truncation, broken interpolation, and layout problems caused by changed copy.
13. Report all changed files and major terminology decisions.

Never blindly replace strings.

Always understand where a string appears before changing it.
